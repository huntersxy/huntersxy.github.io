XProxy 是一套自研代理协议的完整实现，仓库记录覆盖 2026-09-20 首个提交至 0.3.0 的全部 30 次提交。本文按开发顺序梳理各阶段解决的问题，并逐项说明协议机制、工程取舍、实测方法与未完成项。数据来源为仓库源码、设计文档、变更日志、抓包产物与提交历史；无法在观测范围内证实的结论在文中单独标注。

项目概况

客户端在本机提供 SOCKS5 入口，流量经 TLS/WebSocket 隧道到达服务端，由服务端代为访问目标站。隧道外层复用真实域名与证书，与同端口上的普通 HTTPS 站点共存。

协议核心 Go 模块：协议核心、客户端库、服务端、命令行客户端

浏览器扩展 Chrome/Edge MV3，管理浏览器代理模式

威胁模型与设计原则

设计文档为每类对手明确「能看到什么」，不做绝对不可检测的声称。

对手 能看到 看不到
被动监听者 IP 层元数据、流量总量、通信时间、服务端地址；TLS 层仅密文与握手包长 内容、目标域名、应用层协议
流量统计分析者 包长序列、时序相关性、方向性、连接创建频率与时长 无法可靠区分隧道与普通加密流量
主动探测者 对 443 端口做 TLS 握手或非授权访问 认证后才有意义；未授权只得到普通 HTTPS 站点行为
被攻陷的中间跳 只能看到密文流 内容与目标
被攻陷的出口节点 面向目标站的明文、入口转发的源 IP 无法伪造客户端身份

理论上无法隐藏的量为：客户端 IP、服务端 IP、流量总量、大致通信时间。设计目标不是藏住这些，而是在此之上最小化其余可解出的信息。由此导出四条通用原则：

  • 最小固定特征：客户端之间行为一致，不产生一眼可辨的固定字节模式。
  • 标准优先：承载走成熟标准，自定义机制仅在标准无法满足时设计，且不发明加密算法。
  • 通用性：不针对具体设备或产品制定规避规则，只做通用、可重复测试的设计。
  • 可验证：用可测指标衡量，不玄学。

协议机制

以下按「要解决的问题」组织，每项给出机制与可验证的观测结果。

认证握手：无固定前缀与慢哈希口令派生

握手不使用任何固定前缀。客户端问候为 48 字节，前 16 字节是随机盐，后 32 字节是 HMAC-SHA256 标签，密钥由共享口令与该次连接的盐派生。服务端应答同为 48 字节，标签把两个盐绑定在一起，客户端据此确认对端持有同一口令。每个帧整体形如随机字节，被动观察者无法从握手区分该协议与任意加密噪声。

不持正确口令的一方得不到任何可区分的响应：服务端直接关闭连接，没有协议专属错误信息。常量时间比较用于标签校验。

口令到主密钥的派生在 0.3.0 起换为 argon2id，参数取 OWASP 推荐下限（t=2、19 MiB、p=1）[3]。握手字节布局未变，仅派生结果改变，因此抓包后离线猜口令的成本被抬高。代价是派生的计算开销不再可忽略：两条问候加头部认证路径每次连接会跑若干次，实现注释明确该成本须能在小内存低配机器上保持舒适。

参数属协议的一部分：双方必须同版本升级，否则表现为认证失败而无专用错误码。

会话密钥由 HKDF 从主密钥派生，盐取两个握手盐的 HMAC，每条连接独立，因此记录层计数器不会跨连接复用。

外层指纹：让隧道连接长得像浏览器

Go 标准库的 ClientHello 具有稳定且独特的指纹，会把全部连接聚成「一个 Go 程序的 TLS」，与内层协议是否干净无关。该项目的应对是外层使用 uTLS[4] 的浏览器预设，SNI 指向真实站点，使证书与 SNI 校验与普通访客一致。

预设冻结在上游某个 Chrome 主版本，而上游在观测期内未更新预设。09-23 的提交在既有握手构造流程上做手工对齐，未更换依赖，只用其公开 API：

  • 签名算法列表补足到目标主版本的项数与顺序，头位填充每拨现抽的 GREASE 值；
  • 补入后量子签名算法项（该 utls 版本无常量，按裸值写入）；
  • 剔除仅页面握手才出现的扩展；
  • 追加目标浏览器 wss 连接特有的未知扩展，载荷按抓包反推的文法生成，成员集合逐字节等于真值；
  • UA 同步到外层所演的主版本。

ALPN 固定为 http/1.1。这一项一度被误判为偏离：真实 Chrome 的页面加载会协商 h2，但对 wss 连接只提供 http/1.1[8]。抓包真值证实两者是两类连接、两套 ALPN，固定为 http/1.1 正是真实形态。后量子曲线与密套件列表的逐字段比对结果见下文实测一节。

改动的验证方式是逐字段 diff：密套件 15 项逐字相同、supported_groups 与 key_share 含后量子项且长度一致、扩展顺序每连接随机（与 Chrome 同款行为）、非 GREASE 扩展集与真值的对称差为空、ALPN 仅 http/1.1。握手成功率 3/3。

会话恢复（PSK）被依赖缺陷阻塞：utls 该版本存票与取回均正常，但出价侧零物化，纯 Go 基线同样失败（属上游问题，非本项目流程）。处置是保留客户端会话缓存并给两个恢复测试打跳过桩，待依赖升级后原地重开。

长度去相关：按帧类型区分填充

记录层为 [长度:2][密文]，AES-256-GCM[1]，nonce 由方向标签与单调计数器构成，明文前置随机填充以模糊真实长度。

填充策略按帧类型区分：数据帧的长度否则会镜像被隧传协议自身的记录尺寸，从而支持已发表的长度关联攻击，因此数据帧在较宽区间内均匀填充；控制帧体积小且频繁，保留较小上限，避免填充在记账流量上变成纯带宽开销。

两个实现细节值得记录：

  • 判型字节位置。帧的线格式为 [流ID:2][操作:1][长度:2][载荷]，操作字节位于 body[2]。早期实现按 body[0] 判型，而 body[0] 是流 ID 高字节（前 256 个 ID 时恒为 0），导致真实数据帧全被误判为控制帧，宽区间填充在生产上长期失效。该缺陷随 09-22 的提交修复。
  • 随机源宽度。填充长度早期由单字节随机值抽取，任何超过 256 的区间都会塌缩到前 256 个值。改为 4 字节抽取后区间才真正均匀。

填充带来的带宽开销在开发记录中记为约 +6%，属项目自带估计值，未在本文复现测量。

跨层时序：服务端即时微应答

跨层 RTT 的差异是可被检测的侧信道[6]：代理会话的两层错位会让延迟残差额外包含代理到源站的整段距离，与直连的毫秒级处理时延可区分。

该项目的对策是服务端对每个客户端帧立即回一帧确认，把跨层时序关联的互相关峰钉在 1×RTT，与直连服务器的响应形态一致。开发记录中的 A/B 结果是：检测器的超阈占比由 14–75% 降到 0–1%。该数据引用自项目自身的 A/B 记录，本文未独立复现。

兼容性上，路由分发没有默认分支，不支持该特性的旧端会静默忽略确认帧，因此新旧端点可混跑。

连接形态：浏览器形状的连接池

单条隧道上的多路复用让一次握手加一次认证覆盖全部流。这同时改善两件事：握手开销不再随连接数增长；「每打开一个页面就发起完整 TLS 握手」这类本身即为显著固定特征的行为不再出现。

代价是单条隧道成为带宽瓶颈，且中断会同时影响在途流。实现以连接池分摊：默认 3 条（浏览器通常对单个源保持 2–4 条），新流按最省负载分发，池内最老的连接按周期排空轮换，活跃流归零才真正关闭——慢速传输会顺延本轮而非被强杀。轮换周期默认 15 分钟并带 ±30% 抖动，同一时刻只允许一条连接处于排空状态，否则快速轮换与长排空叠加会把服务集合抽干（该情形由测试捕获）。

心跳为 WebSocket ping 帧[2]，基础间隔带 ±1/3 抖动且每周期重抽，仅在空闲达到一个间隔时才发送。断开后重连按倍增减退至上限。

pool_size 与轮换周期均可配，负值分别表示单连接回退形态与禁用轮换，用于快速回退。多路复用的流 ID 为 16 位且只增不回收——回收会让迟到帧被投递到复用了同一 ID 的新流。ID 空间用尽不是错误，而是触发静默轮换：连接按排空流程处理，池补入新连接，开流撞到该状态时在同一次调用内换连接重试，用户侧无感。已耗尽的连接对新流 fail-closed，绝不在没有分配器的多路复用器上继续开流。

主动探测：trojan 式回退

未通过认证的连接不会得到任何协议相关响应。配置了回退地址时，服务端按 trojan[5] 的方式把请求反代到同端口上的真实网站——这是主动探测场景下的事实标准：扫描器看到的只是一个能正常工作的站点。真站不可达时返回与 nginx 逐字节一致的 502 页面，含 Server: nginx 与标准错误页正文；裸 502 与真站故障的形态不同，会成为判据，因此不一致本身就是缺陷。

认证凭证在 WebSocket 升级请求中以标准 Authorization 头承载，服务端标签在 101 响应头回传。由此握手帧不出现在 WebSocket 流内，线上第一条消息已是变长 AEAD 记录；且该头在真实 WebSocket 端点上普遍存在，本身不构成信号。两端凭据尾部各附加随机字节，使令牌长度不成为固定特征，校验只读前 48 字节，因此新旧端点混跑无恙。

可选路径：ClientHello 记录分片

首条 ClientHello 记录可拆成两条 TLS 记录，切点落在 SNI 主机名内部，使任何单条记录都不含完整主机名。依据是审查设备重组 TCP 流但不按 TLS 记录边界重组：项目对某自建入口的对照测量为 TCP 段级分段 0/9 无效、记录级分片 5/5 可握手，同一 IP 上良性 SNI 正常。服务端按 RFC 8446[1] 重组跨记录握手消息，零服务端改动。

该选项按服务器单独开关，默认关闭。理由是真实 Chrome 从不分片其 ClientHello，分片后的首记录本身即偏离浏览器发出的原子记录形态；在健康入口上启用会拿可用连接换更高的可检测性，因此只对 SNI 正被掐断的入口启用。实现为 fail-open：仅首条 write 尝试分片，解析失败或主机名过短时原样放行，绝不破坏流。

同一思路不具普适性：开发记录中对某类通配域名测试的 15 种变体全部失败，说明该名单另有更强规则或独立匹配路径。

多跳链路

客户端可将 2 至 5 台服务器组成链。机制是端到端嵌套（ProxyJump 式）：每一跳在到下一跳的多路复用流上完整运行 TLS、WebSocket 与认证握手，因此中间跳既看不到最终目标，也看不到下一跳的凭据。服务端零改动——承载连接由客户端侧提供即可。

整条链在池中表现为一条连接，因此轮换、最省负载分发、排空语义全部照旧工作。关闭采用逐层放附件的后进先出顺序，断一层则全链收拢。每跳各用各的节点设置，分片等选项互不影响。开发记录中每层带宽开销记为约 +6%，属项目自带估计值。

配置层面，链与单服务器并列，存量配置零迁移；被链引用的服务器拒绝删除并点名校验失败原因。

控制面复用既有隧道

服务端出口管理（切换节点、测速、替换订阅）复用同一条已认证隧道：每次调用开一条逻辑流，目标地址使用保留的 .invalid 顶级域地址，与代理连接区分；无需额外监听，也不需要第二套口令。请求为定长长度前缀加 JSON，因此线格式可扩展而不破坏旧客户端。

订阅替换会拉取远端文件并重载出口，因此保留本机规则、DNS、TUN 与端口设置，仅替换节点与分组，更新前备份、任一步失败自动回滚。服务端未配置控制器时，相关功能对客户端返回明确提示。

工程实践

发布流程。版本号由构建脚本通过链接期变量烧入两端二进制。CI 分两个任务[7]：协议模块在 Linux 上跑 go vet 与带竞态检测的测试；桌面客户端模块在 Windows 上先构建前端产物（主程序以 embed 方式内嵌该产物）再跑检查。本机无 gcc 无法运行竞态检测，竞态覆盖全部依赖 CI 这一条路径。测试规模为 29 个文件、136 个测试函数、5399 行。定向测试采用先编译再指定用例运行的方式，避免测试管道占用标准输入导致阻塞。

凭据清理。某份抓包配置曾把线上口令以明文带入提交历史。处置为：移出版本控制并加入忽略清单，保留本地副本供工具链使用；服务端轮换该口令；重写全部提交历史抹除该内容，重写前留存全量备份于仓库之外。这一项属流程缺陷而非编码缺陷——忽略清单的建立晚于首次提交。

一次未定根因的故障。某台小内存服务器（约 400 MB 内存且当时无交换分区）出现磁盘读速率约每秒 1500 次并渐进死机，表现为服务管理组件超时、随后日志断流，需从面板重启。按项目记录，已排除内存耗尽、坏盘、日志洪泛、核心转储与元数据预缓存；观测窗口内唯一的 I/O 活动方是一个云厂商安全组件，但仅为嫌疑、无实证。根因至今未定位，处置是加装 1 GB 交换分区并调低交换倾向作为保命阀，同时部署每秒一次的进程级 I/O 归因采样器，把时间戳空窗本身作为系统停滞时长的证据。该故障的因果归属属未证实项。

图形界面的取舍。GUI 目标是对齐同类工具的界面组织，包括仪表盘、节点、服务器、连接、日志、设置六个页面与主题切换。托盘常驻用 Wails v2 在 Windows 上不支持托盘 API，因此直接调用系统库手写：独立线程跑消息循环、调用通知区 API、内嵌位图转图标，零新增依赖。托盘图标首次实现全透明——位图创建 API 的像素指针为出参，原实现写入了错误目标；修复后以读回像素的回归测试锁定。非 Windows 平台走空实现，关窗即退出。

实测方法

协议伪装的有效性无法靠推理确认，需要与真实浏览器对照。项目建立了一套抓包对照流程：以独立 profile 冷启动真实浏览器，用密钥日志配合抓包工具解密，分别采集直连腿与走代理腿，再逐字段 diff。

一次对照的结论（目标为某自建入口与一个公共站点）：

维度 直连 走代理 判定
连接建立 每个目标独立直拨出网 每个目标一条明文 CONNECT 落本机，TLS 在隧道内；出网仅剩隧道连接 结构性差异
ClientHello 指纹 逐字段 相同 无差异
后量子曲线与密钥共享 含 相同 无差异
扩展顺序 每连接随机 每连接随机，集合恒同 无差异
ALPN 协商结果 服务端决定 相同 无差异
HTTP 请求头顺序与取值 逐字 逐字一致 无差异
出网 TCP SYN 指纹 本机内核栈 同机同栈 无差异
目标侧观察 源 IP 为家宽 IP 源 IP 为服务端；浏览器 TLS 端到端穿隧 核心差异

结论：除代理腿多出的明文 CONNECT 前导，以及目标侧看到的源 IP 与外层连接形态之外，浏览器自身的 TLS 指纹、ALPN 结果、HTTP 头顺序与取值、内核 TCP 指纹两腿完全一致。

一次数据作废的教训。第一轮对照数据整体无效：本机安全软件启用了加密连接扫描，对所有浏览器 TLS 做中间人中转，上线的是安全软件的 TLS 栈而非浏览器自身的。三条判据同时成立——真实浏览器必带的后量子曲线在抓包中恒定缺失；浏览器写出的密钥日志与抓包中的随机数零交集；全部目标（含自有服务器与公共站点）的指纹统一为同一套中转栈指纹。退出该软件后复测，密钥日志 11/11 命中，后量子项与 GREASE 正常出现。结论：本机任何浏览器 TLS 指纹采集都须先退出该类软件，或把目标域名加入排除项。

这一轮作废同时说明：只看单条连接的指纹不足以判断，跨目标的指纹一致性是更早暴露问题的信号。

范围边界与既有结论

以下为项目已明确的范围判决，记录结论与依据。

项 结论 依据
交互式会话恢复（PSK） 被上游依赖缺陷阻塞，保留惰性缓存与跳过桩 纯 Go 基线同样失败，属上游问题
明文元数据（ALPN 补 h2） 不做 真实浏览器的 wss 连接本就只提供 http/1.1[8]
前端框架固定路径 不再手动配置，每次拨号随机生成 固定路径是跨部署的静态特征；服务端与路径无关
UDP 关联 范围外 主功能是系统代理通道，UDP 从操作系统层即直连，属正常背景流量
伪包干扰 不做 收益不确定，纯噪声且增加排障成本
HTTP/2 传输模式 备胎，暂不实现 仅在 WebSocket 被针对性降速或指纹化时再评估
长短连接分离 否决 按请求建连会使握手率反超真实浏览器并劣化延迟，连接池是折中终点
对抗具体审查设备 不做 只做通用、可重复测试的设计

明确的能力缺口：无连接迁移，隧道重连后已建立的流不会恢复。

未完成项

设计文档给出的演进路线中，以下为未落地部分：

  • 密钥轮换、版本协商、能力协商与向后兼容。当前两端必须同版本，任一端未升级即表现为握手失败。
  • 基于 QUIC 与 MASQUE 的承载评估，以及 UDP 承载。
  • 连接迁移与双栈。
  • 可测指标体系：包长分布、时序相关与指纹差异的常态化测量。当前对照流程为一次性手工执行。

当前已完成项包括 TLS 1.3 承载、强共享密钥认证、帧填充与多路复用、抗主动探测回退、仅使用标准加密套件、连接池与心跳、流 ID 不复用、多跳链路。

小结

六天、30 次提交、6990 行生产代码与 5399 行测试，构成一套可部署的代理协议实现。结构上值得记录的三点：认证与承载在外层标准协议内完成，服务端在多数改动中零修改；抗检测手段全部落在时序、长度与指纹层，而非发明加密算法；每项机制都配有可复现的对照测量，无法证实的一律标注为未证实——包括那台至今根因未明的服务器故障。
