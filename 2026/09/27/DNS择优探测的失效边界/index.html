校园网 WLAN 直连（无代理）下，xiey.work 出现间歇性无法访问，时间 2026-09-27。工具：curl 8.21、nslookup、strings、路由器侧 smartdns 46.1 与其审计日志。结论覆盖解析选路与探测能力边界两类机制：故障的直接原因是 DNS 返回了本网络不可达的边缘节点地址，深层原因是 smartdns 只具备 ICMP 与 TCP 建连两档探测，无法识别「TCP 建连成功但 TLS 阶段被 reset」的地址。数据来源为本机命令输出与路由器日志，未经交叉验证的推断在文中单独标注。

环境

项 值
客户端 校园网 WLAN，网关 192.168.1.1，公网出口 183.251.13.228（福建福州，中国移动）
DNS 路由器 smartdns 46.1；LAN 客户端经 DHCP option 6 指向 192.168.1.1:53
路由器 ImmortalWrt 23.05.6，ramips/mt7621，kernel 5.15.189
对照点 广州 8.134.190.23、香港 47.83.180.74

涉及域名均挂腾讯云 EdgeOne，两个例外：

域名 CDN
xiey.work、www.xiey.work、blog.xiey.work 腾讯云 EdgeOne
xcdn1.xiey.work、xcdn2.xiey.work 无（A 记录直连）
xiey.online Cloudflare

归属

同一时刻 www.xiey.work 超时而 xiey.work 返回 200，刷新后两者结果相反。域名级封锁不会造成子域之间互相矛盾，解析服务宕机也不会出现部分子域可解析，因此变量落在「本次解析到哪个地址」。

用 --resolve 将 SNI 与目标地址解绑后逐个测试：

IP 归属 HTTPS
36.150.72.68 上海，AS56046 中国移动 200
120.221.184.14 济南，AS9808 中国移动 200
175.43.200.34 漳州，AS4837 中国联通 超时

同一张 CDN 上两个节点可用、一个不可用，被挡住的是单个地址而非该 CDN。对 175.43.200.34 的进一步测量：

观测 结果
TCP 22 / 80 / 443 / 8080 / 9000 全部超时
ICMP 4/4 收到，17~39ms
换用 example.com 作 SNI 同样超时
邻居 175.43.200.33 / .35 均返回 200

TCP 全端口被丢、ICMP 放行、按单个地址精确生效，指向路径上设备丢 SYN 而非 SNI 匹配或路由黑洞。

跨观测点交叉验证：

观测点 到 175.43.200.34:443
广州 8.134.190.23 200（0.019s）
香港 47.83.180.74 超时
本机校园网 超时

广州通、香港不通，说明该节点自身的运营商互联状态也有问题。校园网是受影响方之一。

探测能力边界

审计日志给出 smartdns 的选路依据：

该地址 ICMP 通（~16ms），在探测视角下是当时延迟最低的候选。

smartdns 46.1 支持的探测模式（strings /usr/sbin/smartdns 确认）：

模式 探测层级
ping ICMP
tcp:<port> TCP 建连
tcp-keepalive TCP 建连并保持
none 不探测

四档均不含 TLS 握手探测。因此存在一类地址，探测结果与实际可用性系统性背离：

地址 ICMP TCP:443 TLS
175.43.200.34 通 17~39ms 不通 —
124.237.177.164（baidu.com） 通 建连成功（time_connect ≈ 0.05s） time_appconnect = 0
20.205.243.166（github.com） 通 66ms 不通 —

第二行为关键样本：TCP 建连成功而 TLS 阶段被 reset。对 ping 与 tcp:443 两档，该地址均判为健康。三个不同运营商的地址呈现同一模式，不是单次偶发。

区分方法为拆分连接耗时：

connect 有值而 tls 为 0 即属此类。仅做 TCP 建连的探测器一律将其判为可用。任何基于此类探测的择优在相同条件下都会选中该地址。

无效路径

blacklist-ip

不生效。生成配置中 server 行不带 -blacklist-ip 标记，该文件未被读取。

ip-alias

语义为：上游返回 175.43.200.34 时替换为 120.221.184.14 再应答。下发后解析立即变为可用地址，故障消失。

该规则把两个具体地址的对应关系写入静态配置：不支持上游返回第三个地址的情形，不反映 175.43.200.34 当时不可达的原因，且在节点恢复后仍持续改写上游的正常结果。已回退。

speed-check-mode ping,tcp:443 与 tcp:443

两次切换后均仍返回 175.43.200.34。

此处记录一轮错误结论及其纠正过程。首次测试后判定「探测结果被篡改，换任何探测指标均无效」，该判断不成立，原因是清缓存方法有误——详见下节。用正确方法重测后 tcp:443 工作正常：baidu.com 的应答由 4 个地址（含不可达的那个）收敛为 1 个可用地址。

关于「探测被篡改」这一推断：当时的依据是不可达地址的探测延迟（14.619.9ms）低于正常节点（3050ms），差异反常。后续复测显示该地址本身延迟就低（24~51ms，在各候选节点中属正常区间）。观测数据无误，由数据得出的因果推断有误。真实原因即上文所述的能力边界，与篡改无关。该地址的实测延迟属可复现数据，篡改假设属推测且不成立。

缓存清理方法

首次测试使用的方式：

smartdns 在 stop 阶段先将内存缓存写回磁盘，rm 被抵消，重启后读到的仍是旧结果。

正确方式：

判据：cache-persist yes 时，restart 之后 smartdns.cache 必然重新出现。该文件存在即说明缓存未清除。审计日志中的 speed: -0.1ms 同为缓存命中标志，经真实探测的记录会显示具体数值，如 speed: 40.0ms。

处置

关闭择优

none 关闭择优，将上游返回的完整 A 记录一并交给客户端自行尝试与回落。

对照实测（针对「TCP 通但 TLS 被 reset」的地址）：

模式 结果
none 返回全部 A 记录，客户端回落
tcp:443 建连成功即判为健康，8 轮中 3 轮选中不可用地址
tcp-keepalive 同样误判，6 轮中 1 轮

该配置放弃了延迟优选，不再挑选最低延迟节点，代价是非最优节点可能被优先使用。在探测结果可信的网络中这是净损失，在探测结果与实际可用性背离的网络中是必要的取舍。

修正配置分层

生成配置的最后一行是 conf-file /etc/smartdns/custom.conf，该文件最后加载，同名指令覆盖此前全部内容。排查中发现以下覆盖：

指令 UCI 值 custom.conf 值 实际生效
log-level error debug debug
log-size / log-num 64K / 1 128k / 8 128k / 8
serve-expired yes no no

同时 UCI 中标记 enabled '0' 的上游被重新启用，日志确认仍在查询：

整理后 custom.conf 仅保留 UCI 无法表达的两行：

bind 为 UDP、bind-tcp 为 TCP，两者不通用。UCI 的 port 只生成 54 且只覆盖 br-lan/lo，而 LAN 客户端走 192.168.1.1:53。原配置中 53 端口无 TCP 监听，DNS 应答置 TC 位后客户端改用 TCP 重试会直接失败。

上游由 23 个收敛为 8 个（4 个 DoH/DoT 与 119.29.29.29、223.5.5.5、223.6.6.6）。

修正 dnsmasq 重启配额

/etc/init.d/dnsmasq 中 procd_set_param respawn 未带参数，即 procd 默认值 3600/5/5：一小时内崩溃 5 次后永久停止重启。

dnsmasq 是本机唯一的 DHCPv4 服务（dhcp.odhcpd.maindhcp='0'），停止重试后新接入设备无法获取 IP。触发条件为执行 smartdns restart：分三批共测试 12 轮，其中 5 轮出现 dnsmasq 以 exit_code 129（SIGHUP）退出。手动运行（不经 procd）不受影响。

retry=0 表示不限重试次数，取值方式与同机 wpad 一致。

SIGHUP 的来源未查明，已排除 firewall reload、uci commit、dnsmasq reload、配置哈希变化、jail 挂载。

验证

解析稳定性（路由器侧，4 轮）：

域名 解析结果
xiey.work 112.13.210.66、211.136.106.223、117.163.60.28
www.xiey.work 112.13.210.66、117.163.60.28、211.136.106.223
blog.xiey.work 112.13.210.66、117.163.60.28、211.136.106.223

端到端（不走代理）：xiey.work、www、blog、bot 均 200；xcdn1、xcdn2 均 200；对照域名 baidu.com 301、qq.com 302、microsoft.com 301。

TCP DNS：

dnsmasq 保活：手动 kill 后 5 秒内被 procd 拉起。

遗留

xiey.online 的封锁按 SNI 生效，与本组改动无关（该域名走 Cloudflare）。同一 Cloudflare IP 104.21.76.201 更换 SNI：

SNI 结果
example.com 200
cloudflare.com 301
xiey.online 超时（3/3）

处理方式为启用 fragment（TLS 记录分片），或改用 xcdn1 / xcdn2 入口。

175.43.200.34 的封锁在当日稍晚复测时已不可复现：三个 SNI 均返回 200，端口画像 22:closed 80:OPEN 443:OPEN 8080:OPEN 与 120.221.184.14 一致，上游亦不再返回该地址。上文「归属」一节记录的「全端口 TCP 丢弃」为该时间窗内的观测。

结论

封锁键按层分离。解析层返回了本网络不可达的边缘节点地址，上游与本地解析服务对该地址的判断一致，差异在可达性。可达性本身不落在探测可覆盖的层：smartdns 仅具备 ICMP 与 TCP 建连两档探测，而路径上设备对若干地址放行 TCP 建连、在 TLS 阶段丢弃，使 ping 与 tcp:443 均将不可用地址判为健康。关闭择优后完整 A 记录交由客户端回落，这类地址不再构成单点故障。

该类地址在本网络属常态：三个不同运营商的地址（175.43.200.34、124.237.177.164、20.205.243.166）呈现同一模式，换用备用地址（如 github.com 的 140.82.121.3 / .4）即恢复。任何依赖提前探测的选路机制在相同条件下都会命中该失效模式。

配置层面另有两处与本次故障无直接因果、但会造成「配置已改而未生效」的问题：custom.conf 覆盖 UCI 生成项，以及 dnsmasq 的重启配额过小导致其被带死后不自愈。两处均已修正。
