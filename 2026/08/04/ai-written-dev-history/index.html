从一个二次创作资源站到完整工程化平台：小泉动漫二创站 xqecz 的开发历程

记录一下最近几个月维护一个个人项目的过程。

一个项目从「能跑」到「好维护」，中间到底需要经历什么？

项目地址：

GitHub：https://github.com/huntersxy/xqecz

写在前面

最开始做小泉动漫二创站（xqecz）的时候，其实并没有想太多。

目标很简单：

做一个可以上传、浏览、分享二次创作内容的网站。

最初版本更像一个个人作品展示站：

  • 上传图片
  • 内容展示
  • 标签分类
  • 评论互动
  • 简单后台管理

但是随着功能不断增加，项目开始逐渐偏离最初的简单状态。

图片越来越多。

后台功能越来越复杂。

前端页面越来越臃肿。

原本几个文件就能解决的问题，后来需要考虑：

  • 性能
  • 可维护性
  • 安全
  • 自动部署
  • 服务拆分

这也是很多个人项目都会经历的过程：

第一次开发解决的是「有没有」。

后续迭代解决的是「能不能长期活下去」。

根据 Git 提交记录来看，整个项目经历了三个主要阶段：

  1. 早期 Vue + Go 单体开发阶段
  2. 前后端持续优化阶段
  3. 当前 Monorepo + 多服务架构阶段

三个仓库累计提交超过 350 次。

其中当前 xqecz Monorepo 在 2026-07-29 到 2026-08-04 期间完成了 59 次迭代。

当前技术栈：

  • NestJS 11
  • TypeORM
  • MySQL
  • Redis
  • Go 1.25 gRPC Worker
  • Vue 3.5
  • Vite
  • Tailwind CSS
  • Arco Design Vue

一开始：只是一个简单的内容分享站

早期项目结构其实非常简单。

前端：

后端：

当时的想法很直接：

Go 写 API。

Vue 负责页面。

MySQL 保存数据。

Redis 做缓存。

这种架构对于个人项目来说完全够用。

甚至很多小型商业项目也是这么开始的。

但是问题在于：

项目不是静态的。

需求会增长。

比如最开始上传图片：

非常简单。

后来增加：

  • 图片压缩
  • 缩略图生成
  • 图片审核
  • 链接预览
  • 推荐计算

流程变成：

这时候问题出现了：

一次上传可能需要几秒甚至更久。

API 请求时间越来越长。

所以后面开始考虑：

业务接口和耗时任务是不是应该分开？

后端架构调整：引入独立 Worker

后续项目逐渐迁移到了新的 Monorepo 架构。

新的设计：

API 服务负责：

  • 用户
  • 权限
  • 内容管理
  • 数据处理

Worker 负责：

  • 图片转换
  • 缩略图生成
  • 视频处理
  • 第三方服务调用

这样做最大的好处：

即使图片处理任务很慢，也不会阻塞 API。

这也是个人项目发展到一定阶段后很自然的一次架构升级。

图片系统优化：WebP 全链路改造

图片站最容易遇到的问题：

不是 CPU。

而是存储和流量。

尤其二创站这种项目：

用户上传图片尺寸通常比较大。

如果直接保存：

一张图片可能：

几 MB。

几十万个文件之后：

磁盘压力非常明显。

所以后来进行了图片系统优化。

处理流程：

提交记录：

不仅 Worker 支持 WebP。

前端也同步调整。

最终实现：

  • 原图减少体积
  • 缩略图快速加载
  • 首页浏览体验提升

对于图片类网站来说：

优化图片格式往往比优化代码性能更加有效。

前端重构：从能运行到可维护

前端其实是变化最大的部分。

随着页面增加：

  • 首页
  • 内容详情
  • 后台管理
  • 上传页面
  • 主题系统

组件开始越来越复杂。

早期经常出现：

一个 Vue 文件几百行甚至上千行。

例如：

ContentDetailView

最开始里面包含：

  • 评论
  • 举报
  • 内容信息
  • 编辑
  • 弹窗

后来拆分：

拆分之后：

每个组件只负责自己的事情。

维护成本下降很多。

清理历史代码：删除比新增更重要

很多开发者喜欢不断添加功能。

但是项目真正变轻，需要大量删除。

这次优化做了：

  • 删除无用组件
  • 删除重复逻辑
  • 删除废弃依赖
  • 合并重复 composable

其中一次前端重构：

同时处理：

  • API 地址环境变量化
  • 图片懒加载
  • 路由懒加载
  • 代码分割
  • SEO 优化

很多时候：

减少 30% 的无效代码，比增加一个新功能更加重要。

UI 框架迁移：为什么从 Ant Design 换到 Arco

后台管理系统最开始使用：

Ant Design Vue。

但是随着项目视觉方向变化：

发现一些问题：

  • 移动端体验一般
  • 样式定制成本较高
  • 和整体设计语言不统一

所以后来迁移到：

Arco Design Vue。

迁移内容包括：

  • 表单
  • 表格
  • 弹窗
  • 后台布局

提交：

选择组件库其实不是看谁组件最多。

更重要的是：

它是否符合你的项目长期方向。

瀑布流布局优化：一个小功能背后的细节

首页采用了类似图片社区的瀑布流布局。

最开始：

监听窗口变化。

但是实际体验：

快速拖动窗口时：

布局会出现延迟。

甚至停留在错误宽度。

后来改成：

直接监听容器尺寸。

优势：

  • 精度更高
  • 响应更快
  • 避免大量 resize 事件

很多用户体验问题：

并不是大功能造成的。

而是这些细节。

CI/CD 自动部署：从手动上传到自动发布

最开始部署：

简单项目可以。

但是频繁更新非常痛苦。

后来接入：

GitHub Actions。

流程：

过程中踩了不少坑。

pnpm 环境问题

GitHub Actions 中：

pnpm/action-setup

经常出现环境问题。

最后改成：

corepack 管理。

FTP 部署优化

如果每次完整上传：

速度非常慢。

所以增加：

  • MD5 判断
  • 增量上传
  • 构建缓存

提交：

部署效率提升明显。

安全优化：公开项目必须考虑的问题

项目公开运行之后：

安全问题越来越明显。

主要处理：

XSS

用户输入内容：

不能直接渲染。

需要：

  • Markdown 清理
  • HTML 过滤
  • 安全输出

敏感词过滤

早期：

普通字符串匹配。

后来改：

Aho-Corasick 自动机。

复杂度：

一次扫描完成。

Cookie 安全

处理：

  • Secure
  • HttpOnly
  • 动态判断

这些功能开发初期可能感觉不到价值。

但是网站真正上线后：

都是必须考虑的问题。

当前项目结构

现在整体：

├── Go

├── gRPC

└── Media Processing

相比最开始：

现在已经成为一个完整的小型互联网应用架构。

一些个人总结

做这个项目最大的收获：

不是用了多少技术。

而是经历了一次完整的软件生命周期。

从：

到：

很多教程教你：

怎么写一个项目。

但是很少有人告诉你：

怎么维护一个已经写了一万行代码的项目。

真正困难的地方：

不是第一次完成。

而是半年后还能继续修改。

个人项目最大的价值：

就是让你经历这些真实问题。

后续计划

目前项目还在持续迭代。

后续准备继续优化：

  • 推荐算法
  • 图片处理流水线
  • 权限系统
  • AI 辅助功能
  • 内容审核流程

慢慢把这个小项目继续打磨。

毕竟：

一个项目从诞生到成熟，本身就是一次工程能力成长的过程。
