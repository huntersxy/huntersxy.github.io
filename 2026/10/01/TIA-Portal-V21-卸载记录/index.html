2026-10-01 在一台 Windows 11 专业版（build 26300.9550）机器上完整卸载西门子 TIA Portal V21 及其附带组件。卸载前的规模：66 条「应用和功能」卸载项对应 58 个唯一 MSI GUID，59 个顶层产品，16 条服务，27 个 INF 文件含西门子标识（驱动仓库中归属西门子的驱动包为 14 个），3 张根证书，5 条防火墙规则，C:\Program Files\Siemens 单目录 17.15 GB，六个存在的西门子目录合计 18.97 GB。整个过程分两段执行：顶层产品由安装向导界面点选卸载，剩余的叶子组件、服务、驱动、证书、注册表项与目录由命令行收尾。

本文记录四类内容：西门子安装器的组件依赖模型、产品注册表树被卸载程序自身删除后造成的死锁及其恢复办法、命令行批量卸载中反复出现的工具行为陷阱、以及卸载完成后通常被忽略的残留项。文中所有 GUID、路径、服务名与数值均取自本机卸载前的快照和卸载过程的执行日志；无法在观测范围内证实的因果关系单独标注为推测。

环境

项 值
操作系统 Windows 11 专业版，build 26300.9550
主机名 DESKTOP-S3F8RMO
卸载对象 TIA Portal V21 及随附组件（STEP 7、WinCC、PLCSIM、S7DOS 等）
安装器 Siemens Installer Assistant（SIA），版本目录 600

卸载前的快照由脚本采集，内容包括：目录清单、ARP 卸载项、顶层产品列表、驱动 INF、服务、证书、防火墙规则与快捷方式，全部落盘留档。后续每一步清理都以该快照为对照基准。

组件依赖：叶子组件不能单独卸载的原因

西门子安装器把产品组织成三层：顶层产品（Bundle）→ 安装包（SetupPackage）→ 叶子组件（MSI 包）。直接对叶子组件的 GUID 执行 msiexec /x {GUID} 会返回 1603，Windows 事件日志给出的事件 ID 1013 附带完整原因：

也就是说 MSI 层的依赖检查拦住了卸载，被拦的组件仍被上层安装包引用。正确的顺序是先把顶层产品卸掉，顶层消失后叶子组件的引用计数归零，再逐个卸载即可成功。

本次在顶层产品全部移除后，剩余叶子组件由 SIA 的卸载队列分八轮完成，时间戳从 15:25:35 到 16:03:31，各轮的 Intermediate ExitCode after execution queue 依次为 3010, 0, 0, 0, 0, 0, 0, 3010，无失败轮次。3010 表示成功且需要重启。

顶层产品的判定依据是产品名不带 Single SetupPackage 后缀。带该后缀的条目属于叶子层，先卸它们必然触发 1013。

卸载程序删掉了自己的产品注册表

这一环在本次卸载中造成的时间损失最大，且报错信息本身不指向原因。

现象

在向导界面完成第一轮顶层产品卸载后，剩余卸载项在界面上点击卸载时统一报错：

此时「应用和功能」里仍列着几十条西门子条目，但任何一条都无法再卸载。

根因

SIA 枚举可卸载对象的数据源是注册表树：

该树按产品分列子键（另有 Global\Bundles\<product>），每个 EditionMain 子键下记录 GUID、ProductName、Path、Version。SIA 启动时读取这棵树来构造卸载清单，读不到任何产品即输出 no products 并拒绝继续。

问题在于：SIA 在成功卸载一个顶层产品的收尾阶段会调用自身的 Product::RemoveProductRegistration()，把整棵 _INSTALLEDSW 树删除。日志中对应的记录是：

时间戳 14:53:46，对应的日志行是 Siemens Installer Assistant 全局日志中的 <START action="Remove" product="ARP Uninstall" ... context="SIA"> 与同名的 RESULT 记录。也就是说第一轮卸载成功结束后，卸载程序把自己下次启动所需的索引一并删除了。此后每次启动 SIA，日志中的 ProductEnvironment::Initialize() 都报 Requested products count: 0，最终以 Exit Main() with global errorcode=1602 退出。

这一点属于行为观察而非源码结论：删除动作与 RemoveProductRegistration 的对应关系来自日志中的动作名，未做反编译验证。

命令行收尾的工具陷阱

顶层产品卸完后，叶子组件仍走 SIA 的卸载队列，服务、驱动、证书、目录与注册表的收尾清理则全部走命令行。以下行为在本机反复出现，属于工具本身特性而非环境异常。

陷阱 表现 处理
msiexec 不等待 & msiexec.exe /x {GUID} /quiet 立即返回，$LASTEXITCODE 为空串，实际未执行 改用 Start-Process -Wait -PassThru 并读 .ExitCode；用不存在的 GUID 试跑应得到 1605
SIA 静默模式假成功 Start.exe /arpmode /silent 返回 0 但什么都不做 不加 /silent，用 /arpmode /afterreboot 并传 EditionKey
Stop-Service -Force 挂死 服务处于异常 Paused 态时无限阻塞，进程 CPU 恒为 0 改用非阻塞的 sc.exe stop + 轮询状态，超时后 Stop-Process -Id
pnputil 输出本地化 中文系统上按英文 successfully 判成败会全部判负 改用 Get-WindowsDriver -Online 取结构化对象
非提权 Get-WindowsDriver 假阴性 未提权时静默返回空集合，误判为「无西门子驱动」 提权后重新枚举，实测得到 14 个
正则误伤 TIA 会匹配 caTIA（SolidWorks CATIA）与 CredenTIAl 使用 \bTIA\b
标量陷阱 $names = ... | Where-Object {...} 只命中一项时返回字符串，$names[0] 取到首字符 用 @(...) 强制数组
中文脚本乱码 含中文的 .ps1 交 PowerShell 5.1 执行会乱码 提权脚本一律纯 ASCII
reg.exe 返回码 查询不存在的键返回 exit code 1 且 stdout 为空，按文本匹配会误判为「存在」 一律检查 $LASTEXITCODE

函数名也会撞车：把删除函数命名为 Del 会被 PowerShell 内建别名 del 覆盖（别名优先级高于函数），调用时报参数绑定错误。改用不冲突的名字即可。

幽灵注册表键

HKLM\SOFTWARE\WOW6432Node\Siemens 的删除在本次卸载中始终失败。表现是该键处于一种不一致状态：RegQueryInfoKey 报告存在子键，RegEnumKeyEx 能列出子键名，但 RegOpenKeyEx 打开失败；RegDeleteKeyEx、RegDeleteTree、reg delete 全部返回错误码 5（拒绝访问）。

排查过的手段及结果：

  • 检查 DACL 与所有者，权限正常，重写 ACL 后仍为错误码 5。
  • 确认未被标记删除：对该路径调用 RegCreateKeyEx 仍可成功创建。
  • 该键并非 MSI 正在使用的键，无进程持有句柄。

最终使用 advapi32 的 RegRenameKey（Windows 10 1703 起可用）把 Siemens 改名为 Siemens_ZZZ，绕过删除路径腾出名称空间。改名后的键成为惰性残留，其子键 StationManager 同样改名处理。该键不再被任何西门子组件引用，不产生功能影响，是否会在重启后消失未做验证。

同一现象在更早的 V12 残留中表现为挡路的损坏键 StationManager\Catalog，当时也是靠 RegRenameKey 让位，属于同一类问题。

卸载后的残留清查

按类别逐项核对，其中前四类不体现在「应用和功能」列表里，需要单独扫描。

类别 本次数量 位置或标识
ARP 卸载项 66 条 → 0 HKLM\...\Uninstall 两个视图
顶层产品 59 → 0 _INSTALLEDSW、Global\Bundles
服务 16 → 0 服务名含 Siemens / SIMATIC / S7
内核驱动 27 个 INF 含西门子标识 → 0 驱动仓库中 14 个归属西门子，按 ProviderName 判定
根证书 3 → 0 受信任根存储
防火墙规则 5 → 0 入站/出站
字体 47 个文件 / 48 条注册项 西门子专用字体
WER 崩溃报告 4 个目录 Windows 错误报告存档
MUICache 44 条 HKCU\...\MUICache
AppCompatFlags 25 条 兼容性助手缓存
事件日志 0 .evtx 中已无相关记录
安装缓存 323.9 MB SQL Server 卸载后遗留的 \130 安装器缓存

目录层面需要逐一确认的位置：

C:\AX NF ZZ 是西门子许可文件的隐藏存放目录。该目录在卸载后依然存在且不参与任何卸载流程，需要在确认许可不再使用后手动删除。本次删除前做了备份（339 个文件，867840 字节，逐个校验哈希）。

字体、WER、MUICache 与 AppCompat 这几类残留不影响功能，但会在卸载后长期留在系统中，追求干净卸载时需要单独清理。

不属于残留、不要删的对象

清查中命中的以下条目来自其他软件，与西门子无关：

路径 归属
C:\Program Files\Wireshark\diameter\Siemens.xml Wireshark 的 Diameter 字典
C:\Program Files\Wireshark\radius\dictionary.siemens Wireshark 的 RADIUS 字典
D:\Program Files\SolidWorks\SOLIDWORKS CAM\NCEditor\Dll\ncfilter_siemens.dll SolidWorks CAM 的后处理器

按关键字批量删除前先做归属判定，这几条被误删会导致对应软件功能缺失。

核查清单

卸载完成并重启后，按以下顺序确认：

  1. 两个注册表视图下 Siemens、SIEMENS\AUTOMATION、Microsoft SQL Server 分支均不存在。
  2. 「应用和功能」中无任何西门子条目。
  3. 服务列表、驱动列表（Get-WindowsDriver -Online）无西门子归属项。
  4. 受信任根证书与防火墙规则中无西门子条目。
  5. 上述七个目录全部不存在。
  6. 事件日志中不再产生新的西门子相关记录。
  7. 重启一次后复查第 1、3、5 项，确认无自恢复项。

本次最终状态：上述检查项全部通过，仅剩一个已改名的惰性注册表键 HKLM\SOFTWARE\WOW6432Node\Siemens_ZZZ。

小结

卸载这类由厂商安装器统一管理的产品，难点不在清理动作本身，而在两处：一是必须按安装器定义的层级顺序卸载，绕过依赖检查直接删组件会被 MSI 拦下；二是安装器自身的产品注册表树可能在卸载成功后被删除，导致后续卸载入口失效，此时应从安装器自己留下的注册表导出中恢复，而不是手工重建。命令行收尾阶段的多数失败来自工具行为与本地化输出，而非权限或残留本身。
